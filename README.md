# ThermoWatch

**ThermoWatch** is a Unity-based 3D data-centre visualization built for the CGVR course project. It renders a clean, interactive data-centre facility using primitive geometry only — no imported models required:

- **Data hall** — 4 rows × 8 server racks on a 600 mm raised-floor tile grid, with perforated cold-aisle supply tiles
- **Cooling stations** — 4 CRAC units with dark charcoal bodies and blue lattice discharge tops
- **Power infrastructure** — UPS-A / UPS-B, battery cabinet (BATT-A), LV switchgear, row-end PDUs and network cabinets, overhead cable trays
- **Safety & services** — FM-200 fire-suppression cylinders, chilled-water (blue) / fire-suppression (red) process pipework, catwalk railings, overhead light strips
- **UI** — press **L** to show or hide all billboard labels

Everything in the scene is regenerated by a single editor script (`DataCenterGuard → Rebuild Data Center Scene`), so the layout is always reproducible from code.

## How to clone and open the project

1. **Install Unity Hub** → <https://unity.com/download>, then install **Unity 6000.6.9f1** through
   *Installs → Install Editor* (any module set is fine; Linux editor needs no extra modules for this project).

2. **Clone the repository:**

   ```bash
   git clone https://github.com/VishalBhat07/CGVR-Lab-EL.git
   cd CGVR-Lab-EL
   ```

   > The original scene came from [GowdaVarun/ThermoWatch](https://github.com/GowdaVarun/ThermoWatch).

3. **Open the project in Unity Hub:**
   *Projects → Open → select the cloned folder* (the folder that contains `Assets/`).
   Unity Hub will detect version 6000.6.9f1 and offer to open it with that editor — click **Open**.

4. **First import:** Unity will import all packages and compile scripts (1–3 minutes).
   The `Library/` folder is created locally and is **never** committed, so every collaborator gets a fresh import — that is expected and correct.

5. **Open the main scene:**
   In the Project window navigate to `Assets/Scenes/DataCenterGuard.unity` and double-click it.

6. **Run it:** press **▶ Play** (top-center of the editor).
   - Right-mouse drag → orbit the camera
   - Mouse scroll → zoom
   - **R** → reset the camera view
   - **L** → show or hide billboard labels

7. *(Optional)* To regenerate the whole facility from code, use the editor menu
   **DataCenterGuard → Rebuild Data Center Scene** (exit Play Mode first).

## Committing your changes (for collaborators)

Unity projects have two golden rules:

1. **Never commit `Library/`, `Temp/`, `Logs/`, `UserSettings/`** — the repo's `.gitignore` already blocks them.
2. **Always commit the matching `.meta` file next to every new asset** — Unity's asset GUIDs live there; losing a `.meta` breaks references for everyone else.

### Everyday workflow

```bash
# 1. Pull the latest work before you start editing
git pull --rebase

# 2. Check what changed (Unity scenes/.meta files change often)
git status
git diff --stat

# 3. Stage your work — add specific files rather than blindly adding everything
git add Assets/Scripts/UI/MyNewScript.cs Assets/Scripts/UI/MyNewScript.cs.meta

# 4. Commit with a clear, present-tense message
git commit -m "Add hotspot overlay to rack visuals"

# 5. Push to GitHub
git push origin main

# 6. If others pushed while you worked, rebase and push again
git pull --rebase
git push origin main
```

### Branching (recommended for anything non-trivial)

```bash
git checkout -b feature/label-toggle     # create + switch to a feature branch
# ... make changes, then:
git add <files>
git commit -m "Improve label toggle layout"
git push -u origin feature/label-toggle  # first push sets the upstream
# open a Pull Request on GitHub and get the change reviewed before merging
```

### Handy to know

- **Scene conflicts:** only one person should edit `DataCenterGuard.unity` at a time. Prefer editing scripts (like `DataCenterSceneBuilder.cs`) over hand-editing the scene.
- **Large binary assets:** keep them minimal. If one is unavoidable, commit it with Git LFS: `git lfs track "*.psd"`.
- **Don't rename assets from your OS file manager** — rename inside the Unity editor so the `.meta` file stays in sync.

## Thermal analysis

Open `DataCenterGuard` in Play Mode. The heatmap appears by default. Press **H** or click **Hide heatmap** to toggle it. The overlay shows a horizontal air-temperature slice at 1.15 m and uses a fixed 18–42 °C color scale. Temperatures outside that range use the endpoint colors.

- **Demo** animates illustrative hotspots behind the racks and cooler air in the two cold aisles.
- **Normal**, **Load spike**, and **CRAC outage** run the thermal model. Use the two sliders to change the load per rack and the total load on the spiking rack. Switching directly between these modes preserves the temperature field, so selecting **Normal** after an outage shows recovery.
- **Reset temperatures** returns to the warmed-up normal baseline at the current rack load. **Compare at 180 s** independently runs all three scenarios from the same baseline and reports their peaks and the time to recover after restoring cooling. The live display runs at up to 12 simulated seconds per real second.

### Model and assumptions

The 22 × 20 grid uses 0.6 m cells, a 1 m effective air-layer depth, and a 0.1 s time step. For each cell, the change in stored heat is the sum of heat exchanged with neighboring cells, sensible heat carried by prescribed rack airflow, heat released by the racks, and heat removed by the cooling units. The domain boundary is insulated. Neighboring cells exchange heat using an effective mixing diffusivity of 0.12 m²/s.

Each of the 32 racks sends 0.24 m³/s from its front inlet to its rear exhaust and adds its configured electrical load as heat. The return loop assigns each rack to the cooling unit nearest its inlet. A running CRAC cools its return streams toward 18 °C, up to 12 kW per unit. During an outage, the affected loops recirculate their return air without cooling. The assumed volumetric heat capacity of air is 1,206 J/(m³·K).

This is a 2D model with prescribed circulation and assumed operating values. It treats the hall as a single air layer and does not resolve the raised-floor plenum, 3D airflow, rack obstructions, or heat storage in equipment and walls. Use the results to compare scenarios within the model.

### Default scenario results

The baseline starts at 22 °C and runs with normal cooling for 900 simulated seconds. Each scenario then runs for 180 simulated seconds at the default settings.

| Scenario | Peak air | Warmest rack inlet | Heat added | Heat removed at 180 s | Peak location (Unity X, Z) |
| --- | --- | --- | --- | --- | --- |
| Normal, 1 kW per rack | 21.5 °C | 18.8 °C | 32.0 kW | 32.0 kW | −2.7 m, −2.1 m |
| Rack C01 at 4 kW | 26.3 °C | 19.2 °C | 35.0 kW | 35.0 kW | −3.3 m, −1.5 m |
| CRAC-1 offline | 34.9 °C | 33.3 °C | 32.0 kW | 29.9 kW | −2.7 m, −6.3 m |

The load spike mainly raises the temperature near the rack exhaust. The outage raises both aisle and inlet temperatures, with roughly 2.1 kW still accumulating in the modeled air at 180 s. After restoring CRAC-1, the peak air and warmest inlet temperatures both return to within 0.5 °C of the normal values after 158 simulated seconds.

### Rack placement analysis

In Play Mode, choose **Analyze layout**. Select the slot currently occupied by the rack with the peak load, then click **Run comparison**. Set the base and peak loads in one of the live model modes before running the comparison. The recommended swap and its two slot IDs appear in the hall without moving the scene geometry. Use **Current layout** and **Recommended layout** to inspect the same scenario and temperature scale. Each heatmap shows the time of its layout's peak rack-inlet temperature within that scenario.

The benchmark keeps rack positions and orientation, base airflow, total power for each scenario, and installed cooling capacity fixed. It tests the current placement and all 31 single swaps involving the peak-load rack. The test uses a uniform nominal load during a shared 900 s warm-up, then tests each placement for 180 s under nominal load, peak load with full cooling, and peak load with each of the four CRAC units offline in turn. An inlet reading is sampled at each second, including the starting condition.

ThermoWatch minimizes the worst sampled rack-inlet temperature across the six cases. At 0.01 °C resolution, ties favor lower integrated inlet-temperature exceedance above the 27 °C reference in the limiting case, then retain the current slot if its score is tied. The exceedance metric sums the temperature above 27 °C over time and across racks, in rack-degree minutes. The other comparators retain the current placement, place the peak load in the least-loaded CRAC service group under nominal load, or select the slot by peak inlet temperature with full cooling.

With 1.0 kW base load, a 4.0 kW burst at C01, and the supplied model assumptions, the default benchmark gives:

| Method | Peak-load slot | Worst case | Peak inlet | Racks above 27 °C in that case |
| --- | --- | --- | --- | --- |
| Current layout | C01 | CRAC-1 offline | 34.65 °C | 10 |
| Balance cooling load | C01 | CRAC-1 offline | 34.65 °C | 10 |
| Optimize with all CRACs active | B05 | CRAC-3 offline | 35.22 °C | 10 |
| Optimize across outage cases | D02 | CRAC-3 offline | 33.42 °C | 10 |

The outage-aware swap improves the modeled worst-case peak by 1.23 °C, while the model still predicts inlet temperatures above the reference. Choose **Export summary CSV** to save the 192 scenario results to Unity's application-data folder. The Unity Console prints the path.

This benchmark considers interchangeable rack slots and one burst load. The scene has no circuit or cabling inventory. The airflow and recommendations still require independent validation before use for physical placement.


### Per-rack temperature traces

After running **Analyze layout**, choose **Export rack traces CSV**. The Unity Console prints the saved file path. The export includes all 32 slots at one-second intervals from 0 through 180 s for each of the three shortlisted layouts and all six scenarios. Time zero is the end of the shared 900 s warm-up. It includes the peak-load slot, offline CRAC, rack position and yaw, inlet sample-cell center, base and peak power settings, actual rack power for that case, and the modeled inlet temperature. Scenario names and the offline-CRAC column distinguish single-unit outages.

Use Python with Matplotlib to create a comparison figure from a trace export. The default figure shows the warmest inlet at each time for each layout. Add `--rack` to follow one fixed slot.

```bash
python3 Tools/plot_rack_traces.py rack-temperature-traces.csv comparison.png
python3 Tools/plot_rack_traces.py rack-temperature-traces.csv rack-A08.png --rack A08
```

For a CFD comparison, match the exported Unity X/Z coordinates to the facility geometry and sample at the corresponding inlet cell center and height. Use the same warm-up, time origin, rack power, and CRAC outage for each matched case.


### CFD or testbed comparison

Export the reference temperatures at the same rack-inlet positions and sample times as the ThermoWatch trace. Use these columns:

```csv
layout,peak_load_slot,scenario,offline_crac,time_s,rack_slot,inlet_c
current,C01,CRAC outage,CRAC-1,0,A01,18.8
```

The example shows one row. Use the exported peak-load slot for each of `current`, `all_cooling`, and `outage_aware`. Label cases `Normal`, `Peak load`, or `CRAC outage`. Set `offline_crac` to `CRAC-1` through `CRAC-4` for an outage and leave it blank otherwise. Provide one reading in °C for each rack and every whole second from 0 through 180 in each selected layout and scenario.

```bash
python3 Tools/compare_cfd_traces.py rack-temperature-traces.csv cfd-traces.csv --output comparison.json
python3 Tools/compare_cfd_traces.py rack-temperature-traces.csv cfd-traces.csv --cases all --output comparison-all.json
```

The default comparison covers peak load with all cooling active, CRAC-1 offline, and CRAC-3 offline. Use `--cases all` to include normal operation and all four single-unit outages. The tool rejects missing and duplicate readings and mismatched peak-load slots. Extra CSV columns are allowed.

The JSON reports MAE, RMSE, and signed bias (ThermoWatch minus reference). It shows the peak inlet temperature, first peak time, and all racks that reached that peak. It ranks layouts by peak inlet temperature for each case and by the worst peak over the selected cases. Equal peaks share a rank. If an independent analysis estimates the uncertainty of the reference's worst-case improvement, pass it in °C via `--uncertainty-c`. The report checks whether the measured improvement exceeds that value. The ranking and uncertainty comparison apply only to the selected cases.
